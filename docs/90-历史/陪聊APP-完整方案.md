## 一、项目定位与核心约束

**目标**：做一个个人自用的安卓陪聊 App，接入ai模型后像真人一样会记住用户、会时不时主动找用户聊天，主动消息有真实内容（基于记忆和上下文生成，而不是从话语池随机挑）。

**已确定的硬约束**：

1. **纯客户端，无服务器、电脑不常驻。** 用户之前评估过 Magpie 反代网关方案，因需要常驻设备而放弃。
2. **APP内由用户自行填写 API Key。**
3. **安卓手机，已 root。** 可以利用 root 加白名单解决保活/自启动问题。
4. **以后可能分享给别人**，届时 API Key 由每个用户自己填。
5. **进程平时不常驻**，靠系统级调度在需要时唤醒，执行完就退出（省电）。
6. **通知效果**：像微信那样在手机屏幕顶部弹出——用本地高优先级通知（不是网络推送），不需要 FCM/厂商推送通道。

### 模块 2：三层记忆系统

| 功能     | 说明                                                   |
| ------ | ---------------------------------------------------- |
| 短期记忆   | 最近 30 天的事，带淡忘分，随时间衰减                                 |
| 长期记忆   | 关于用户的稳定事实、偏好，跨会话记住                                   |
| 每日日志   | 按日期存事件流水，带绝对时间戳                                      |
| 语义去重   | 新记忆和旧的语义重复就更新旧的，不膨胀                                  |
| 时间锚点   | 「下周三」当场换算成绝对日期，不会失效                                  |
| 淡忘机制   | 不删除，只是越来越难被召回，内容一直可查                                 |
| 记忆管理界面 | 查看 AI 记住了什么，支持手动编辑/删除                                |
| **记忆干预** | 手动新增一条记忆（如「记住我对花生过敏」）、删掉错的                         |
| **心情（本次定）** | 存一个 mood 字段（normal/happy/low），每次互动后更新，生成主动消息时带入，影响语气。**用一次额外的独立模型调用来更新**（见下） |

**心情 mood 的更新机制（本次定，用额外模型调用）**：

- **触发**：每轮对话结束（用户发消息 + 模型回复完）后触发一次
- **做法**：另发一次**独立的 API 请求**（不复用主对话的会话 ID / conversation_id），只带「system 指令 + 最近 3~5 轮对话 + 当前 mood」，要求模型只输出 JSON：`{"mood": "happy|normal|low", "reason": "一句话理由"}`
- **模型选择**：建议用同一家的**轻量便宜模型**（情绪判断不需要强模型）
- **不占主对话上下文**：mood 请求是独立会话，输入输出**不写回主对话的历史数组**，主对话能装多少历史不受影响。⚠️ 实现上务必用全新会话、不复用任何会话 ID，否则会串上下文
- **成本**：每轮多一次付费请求 + 一点延迟；不挡用户看回复——主回复先显示，mood 分析后台跑
- **失败兜底**：模型输出格式不对/超时 → 保持原 mood 不变，不影响主对话

**追问型任务 / 监督链（本次重写，按开发者描述）**：

核心：**任何事件预约任务创建时，都由额外 AI 判断三件事——要不要追问、间隔多久、什么条件停止**，不靠「监督」这类关键词硬触发。用户举的例子：「提醒我 7 点去吃早餐」——额外 AI 判断这是值得追问的任务、间隔 15 分钟、停止条件=用户说正在吃早餐或主动取消。

- **创建时（额外 AI 判断）**：用户说一句带时间的话（「7 点提醒我吃早餐」），主对话正常回复的同时，额外 AI 抽取一条结构化任务存本地：
  ```json
  {
    "type": "event_with_followup",
    "task": "吃早餐",
    "first_at": "2026-11-21T07:00",
    "need_followup": true,
    "followup_interval_min": 15,
    "stop_condition": "用户表示已吃早餐 或 主动取消（如『来不及了不吃了』）",
    "state": "pending",
    "followups_done": 0
  }
  ```
  - 若额外 AI 判断 `need_followup=false`（如「7 点提醒我看个新闻」），就退化为普通一次性提醒，不进追问链
- **到点流程**：
  - 7:00 到点 → 发消息「吃早餐没？」（在主对话里正常显示 + 通知/语音）；state=waiting_reply
  - 用户回复后，用**额外 AI 判定**两件事：① 这次回复的 mood ② 是否满足停止条件 / 是否还要继续追问。可与 mood 更新**合并成一次独立模型调用**（不占主对话上下文），省调用
- **循环判定**（每次追问后都走）：
  - 回复「吃了 / 正在吃」→ 满足停止条件 → 对话 AI 回「好，那你慢慢吃」→ state=done，结束
  - 回复「还没」→ 不满足 → 对话 AI 回「快去吃早餐」→ 挂 15 分钟后闹钟 → 到点再发「快去吃早餐」→ 再判定，循环
  - 回复「上课来不及了就不吃了」→ 额外 AI 判定为主动放弃/取消 → state=done，结束
  - 没回复 → 到点照常追问（温和提醒）
- **停止条件的本质**：是**语义判断**（额外 AI 理解「吃没吃 / 放不放弃」），不是关键词匹配——所以「来不及了不吃了」这种变体也能正确识别为停止
- **绕过闸门**：追问属于用户指令链，绕过决策闸门（冷却/降频/无钩子），但受勿扰模式约束
- **寄生在现有调度**：不另起调度——每次 WorkManager/AlarmManager 醒来先看有没有到点的追问任务，有就按状态机处理，没有再走主动消息逻辑
- **独立模块**：状态机复杂度高于其他模块，单独实现、单独测试

**两个本方案补的默认（开发者未明确，先按此实现，可改）**：
1. **绝对追问上限**：开发者说「循环下去直到停止」，但若用户一直不回、也不取消，会无限追问变骚扰。默认设 `max_followups`（建议 5 次）兜底——到上限仍无明确结果就停止并发一句「那我不打扰你了」。要改成真的无上限也可，但风险自负。
2. **额外 AI 判断失败的兜底**：判断「要不要追问/停止条件」的调用若超时或输出格式错 → 默认停止追问（宁可少追，避免骚扰），任务转 done。

### 模块 3：主动发消息

**三条触发线**：
1. **定时兜底**：WorkManager 每几小时检查一次，设「有网才执行」约束
2. **事件预约**：setAlarmClock 精确唤醒，仅用于「明天面试」这类**一次性、有具体时间点**的未来事件
3. **沉默检测**：长时间没互动触发，并入定时检查里判断

**统一待发队列 + 优先级调度（本次新增，已定，A+C 方案）**：

- 问题：三条触发线各自独立唤醒，可能同一秒都决定发消息 → 连发两条；且「该不该发」的规则散在各处容易漏。
- 做法（A）：所有触发源（定时兜底 / 事件预约 / 追问链 / 特殊日期 / 环境关心）**不直接发消息**，而是往一个「待发队列」投一个任务，由**一个调度器串行处理**——每次只处理一条，处理时统一检查冷却/勿扰/每日上限，规则只写这一处。
- 优先级（C）：出队时按等级选，同级按时间先后：
  ```
  用户指令提醒（叫床/监督/一次性事件） > 追问链 > 特殊日期/节日 > 环境钩子 > 定时兜底闲聊
  ```
  高优先级先处理；同一时刻多条时低优先级的丢弃或顺延到下次。
- 效果：并发竞态从根上消失（串行），重要的不会被闲聊挤掉，去重规则集中一处好维护。
- 注：不采用「原子锁 + 上次发送时间」的 B 方案——它只挡并发但可能让闲聊抢在叫床前面发出去。

**指令型提醒绕过决策闸门（本次新增，已定）**：

- 区分两类消息：**AI 自发的主动消息**（走下面的决策闸门）vs **用户明确指令的定时提醒**（如「明天 7 点叫我起床」「8 点提醒我做事」）。
- 用户明确指令的提醒：**绕过**冷却时间、回复率降频、无钩子不发这三条闸门（否则你让它叫床它可能不叫），到点必须执行。
- 但仍受**勿扰模式**约束（那是用户自己设的）——勿扰区间内按勿扰规则的设定决定是否发语音/通知。

**决策闸门**（纯规则，不调模型，避免烧 token；仅适用于 AI 自发的主动消息）：
- 勿扰模式：自动勿扰模式开启且处于勿扰时间区间时，按该模式的设定处理（不发语音；是否发通知由该模式的独立开关决定）——已取代原先硬编码的 23:00–07:00 静默时段
- 冷却时间：距离上次任意交互 < 2 小时不发
- 回复率驱动：近 7 天回复主动消息的比例，高就缩短间隔，低就拉长（<20% 降到一天一次）
- 全局上限：一天最多 3 条
- 无钩子不发：记忆钩子和环境钩子都召不出合适的就跳过，宁可少发不发散话

**召回钩子**（A 方案记忆的核心收益）：
- 钩子选择顺序（已定）：环境钩子优先于记忆钩子；只有没合适的环境钩子时才从三层记忆按「时间新鲜 + 重要 + 久未提起」评分选 TOP 1
- 评分公式：`得分 = 时间新鲜度 × 权重 + (当前时间 - 上次提起) × 久未提及加分 - 淡忘分`
- 发过的钩子打「已提起」标记，避免复读
- **快捷反馈（本次新增，规则已定）**：消息/通知旁加「别再提这个」按钮
  - 点 1 次：该记忆降权 + 进入 **30 天冷却期**，期间不作为主动消息钩子；冷却期过后负分衰减、恢复正常参与召回
  - 点 2 次：**永久拉黑**，再也不作为主动消息钩子（但记忆本身不删除，用户主动问仍能答）
  - **回复即加分（本次新增）**：用户没点「别提这个」、而是回复了这条主动消息 → 视为对该记忆**加分**，后续更容易被召回
  - **默认不加不扣（本次新增）**：用户什么都没做（既不回复也不点「别提这个」）→ 该记忆分数不变，只按淡忘分自然衰减。不存在「不回复就扣分」
  - 记忆被否不影响新记忆产生：只要继续对话，模型仍会沉淀新记忆，过段时间又有钩子可用
  - 短期全被否的处理：若当前所有记忆都在冷却/拉黑状态，这段时间就没有记忆钩子，主动消息退回只用环境钩子（天气/时间）；仍无钩子则按「无钩子不发」跳过，不算 bug
- **特殊日期（本次改定）**：生日/纪念日**存进长期记忆**（只录一次，不设循环闹钟），在每天定时检查时加一步「今天是否命中某条重要记忆里的日期」，命中就**强制设为当天钩子**优先发祝福——不用每年重设、不会漏。（一次性事件仍走事件预约的精确闹钟，两者并存但统一成「到点检查」逻辑。）
- **内置节日表（本次新增，用户无需录入）**：App 自带一份节日表，不需用户把节日写进记忆、也不用模型推算日期：
  - **公历节日**（国庆 10.1、元旦 1.1、劳动节 5.1、儿童节 6.1 等）：日期写死在表里
  - **农历节日**（春节、元宵、端午、七夕、中秋、重阳）：**预生成映射表**——开发时提前算好未来若干年（如 2026–2036）每个农历节日对应的公历日期，以静态 JSON 打包进 App；运行时**只查表、不跑农历算法、不引入第三方农历库**（零依赖、零运行时计算、省电）。预先算表可用工具/库，License 不影响 App 本身。映射表有年限，2036 年以后发新版本更新即可
  - **日期命中**：每天定时检查时，同样检查「今天是否命中节日表」；命中就强制设为当天钩子
  - **基于人设生成祝福**：命中节日后不直接发模板话（如「国庆快乐」——像群发、不像真人），而是把「节日 + 你的人设 + 最近对话」交给模型，生成一句带你俩语境的祝福
  - 农历库方案作为备选记录于此，但本方案采用预生成映射表，不引入依赖

**生成与送达**：
- 生成层：钩子（记忆钩子或环境钩子）+ 关系摘要 + 最近几条对话 + mood + 环境数据 → 官方 API 生成一句自然的话
- 送达层：本地 `IMPORTANCE_HIGH` 通知，顶部弹出，点击直达对话页并把这条消息插入对话历史
- 语音层（本次新增）：主动消息生成后，若语音开关开启，调用系统 TTS 引擎把这条消息念出来（详见模块 5）
- **语音的勿扰规则（本次新增）**：自动勿扰模式开启且当前处于勿扰时间区间时，消息**不自动念语音**；该区间内是否照常发通知，由用户单独设定（见模块 8）

**测试模式（本次新增）**：设置里加「立即触发一次主动消息」按钮，手动跑完整链路（决策→召回→生成→通知→语音），方便调试，不用等闹钟。

### 模块 4：省电设计

| 要点       | 说明                                                                            |
| -------- | ----------------------------------------------------------------------------- |
| 进程不常驻    | 靠 BroadcastReceiver / WorkManager Worker 被系统拉起，执行完自然结束。绝不开前台 Service 常驻       |
| WakeLock | 唤醒后拿 `PARTIAL_WAKE_LOCK`，任务结束 release                                         |
| 有网才干活    | WorkManager 的 `setRequiredNetworkType(CONNECTED)`；AlarmManager 则自己检查，没网就重新预约  |
| Doze 穿透  | 定时兜底用 `setExactAndAllowWhileIdle()`；事件预约用 `setAlarmClock()`（最高优先级，能穿透深度 Doze） |
| 国产 ROM   | 引导用户加电池优化白名单、允许自启动、允许后台运行（root 可自动处理）                                         |
| 不做预热     | 第一版不提前唤醒预热，到点直接生成+发                                                           |

### 模块 5：语音输出 / TTS

| 功能          | 说明                                                                             |
| ----------- | ------------------------------------------------------------------------------ |
| 调用系统 TTS 引擎 | 用安卓系统自带的 `TextToSpeech` API，不内置语音合成模型；检测设备上可用的 TTS 引擎（系统默认 / 用户安装的第三方引擎），让你自己选 |
| 对话内容朗读      | 聊天界面里：点一条消息可以单独朗读；也支持「自动朗读」——模型回复显示完后自动念出来                                     |
| 主动消息语音      | 平时随机/定时的关心消息，除了顶部通知，同时用 TTS 念出来（开关开启时）                                         |
| 语音开关        | 设置里一个总开关控制语音输出；关闭后对话朗读和主动消息语音都不触发                                              |

**实现要点（供讨论）**：

- **引擎选择**：`TextToSpeech` 初始化时枚举 `getEngines()`，列出设备上已安装的引擎让用户选；设一个默认引擎
- **无引擎降级**：设备上没有可用语音引擎时，明确提示「请安装语音引擎」，不内置离线引擎，不做其他降级
- **朗读时机（已定）**：
  - 对话回复：**整段生成完后一次性念**（不逐字念、不边生成边念）
  - 主动消息：**通知弹出后后台自动念**，不需要用户点开通知；设置里可关
  - **自动勿扰（本次新增）**：勿扰模式开启且处于勿扰时间区间时，主动消息**不自动念语音**；该区间内是否照常发通知由用户单独设定（见模块 8）。对话里的手动点按朗读不受勿扰模式限制——勿扰只管「自动发声」，不管用户主动点的播放
- **TTS 初始化**：异步（有 `onInit` 回调），要处理「初始化未完成就收到消息」的队列问题；主动消息场景在后台唤醒时，注意 `TextToSpeech` 在后台 Service 的可用性
- **进程短暂停留（已定）**：App 被唤醒后可停留 **5 分钟**（以便用户进入 App 续聊）；语音朗读期间保持进程与 WakeLock 存活，播完即释放；5 分钟到即结束，不做更长驻留
- **语速/音色**：`setSpeechRate()` / `setPitch()` 可调，建议设置里给个语速滑块

### 模块 6：环境感知（位置 / 天气 / 时间）

**目标**：让 AI 能基于「现在几点、你在哪、天气如何」主动关心你，比如「太晚了别熬夜」「今天有雨记得带伞」。

| 数据源  | 获取方式                                                    | 说明                                           |
| ---- | ------------------------------------------------------- | -------------------------------------------- |
| 时间   | 系统时间 `System.currentTimeMillis()`                       | 零成本，直接可读；时区按本机                               |
| 位置   | Android `FusedLocationProviderClient.getLastLocation()` | **后台只取系统缓存位置，不主动发起定位**——几乎不耗电，也不弹持续定位通知      |
| 位置更新 | **每天第一次打开 App 时**（前台）调一次 `getCurrentLocation()` 更新缓存    | 一天一次足够；若用户已手动指定城市，则不再自动定位                    |
| 天气   | Open-Meteo API（免费、无需 Key、支持中国区 CMA 数据）                  | **前台打开 App 时自动联网拉一次并缓存**，后台唤醒只读缓存、不联网拉天气（已定） |

**位置权限**：申请 `ACCESS_COARSE_LOCATION`（粗略位置）即可，够用于天气；不申请精确定位、不做位置追踪、不存历史轨迹。首次使用时弹权限说明。

**关于「申请权限能不能解决缓存位置太旧」**：权限只是允许读取，不能让缓存变新。缓存由系统里其他 App 的定位请求刷新，你若不用地图类 App，缓存可能几天不更新。解决办法（已定）：**每天第一次打开 App 时**前台更新一次——后台永远只读缓存，不主动定位；**一旦用户手动指定了城市，就完全不再自动定位**（以手动城市为准）。

**环境数据怎么变成关心消息**：

- 决策层用**纯规则**判断环境是否值得关心（不调模型，省 token）：
  - 时间 > 23:00 或 < 05:00 → 「太晚了别熬夜」类
  - 未来几小时降水概率 > 阈值（如 50%）→ 「有可能下雨记得带伞」类
  - 温度骤降 / 高温 → 相应提醒
  - 同时满足多条时，分成多条按顺序发出
- 判定为值得关心后，把环境数据（时间 + 天气代码 + 温度 + 降水概率 + 位置城市名）作为**环境钩子**喂给生成层，让模型用你的人设语气说出这句关心，而不是套模板
- **环境钩子优先于记忆钩子（已定）**：两者共同进入决策闸门（勿扰模式、冷却、每日上限仍生效）；当两条钩子都存在时，先选环境钩子（下雨/熬夜有时效性，错过就没意义），没有合适的环境钩子再用记忆钩子
- **烦人度控制（已定）**：同一类环境提醒（如带伞）要有冷却期，一段时间内不重复；环境关心消息也统计回复率，和记忆钩子一样参与降频——别连着几天唠叨同一件事

**实现要点（供讨论）**：

- 天气拉取（已定）：前台打开 App 时自动联网拉一次天气并存缓存（和更新位置一起做）；后台唤醒时只读缓存、不联网拉天气
- 代价（已知）：若用户几天不开 App，缓存天气会旧，后台发的天气关心可能不准——用缓存时间戳判断，过旧（如超过 24h）则跳过天气类关心，不当次联网补拉
- 位置失败降级：定位权限没给 / 拿不到位置时，允许用户**手动指定城市**，或退化为只用时间做关心；手动指定后不再自动定位
- 隐私：位置信息只用于当次天气请求，不落库、不上传；App 内说明清楚

### 模块 7：语音唤醒与语音输入（本次新增，含重大设计冲突，待决策）

| 功能 | 说明 |
|---|---|
| 语音唤醒 | 类似小爱同学，说唤醒词（如「你好小陪」）直接唤起 App 进入对话 |
| 语音转文字 | 说话 → 本地 STT 转文字 → 发给大模型 → TTS 念回复，全程语音对话 |
| 快捷入口（本次改定） | **通知栏常驻快捷入口**：常驻通知 + PendingIntent，点一下直接进对话；普通 App 即可实现，不需要 root；进程仍可休眠，点通知才拉起 |

**⚠️ 与省电设计的根本冲突（必须先决策）**：

- 语音唤醒要求**持续开着麦克风听唤醒词**，Android 8+ 下后台用麦克风必须用**前台服务**（常驻通知），这和模块 4「进程平时休眠、闹钟到点才醒」正面冲突。
- **关键澄清：小爱同学省电不是因为权限高，而是因为它走厂商专用的 DSP/低功耗协处理器**——那颗芯片专听唤醒词，主 CPU 和麦克风大部分时间睡着。这个硬件通道普通 App 拿不到，**root 也拿不到**（需要厂商 HAL 层支持，不是权限开关能解决的）。
- **root / ADB 能解决什么、不能解决什么（本次核实）**：
  - ✅ 能解决「后台别被杀」：ADB（无需 root）可加 Doze 白名单、允许后台运行、免待机冻结、授予运行时权限，典型命令 `adb shell dumpsys deviceidle whitelist +包名`、`adb shell cmd appops set 包名 RUN_ANYWHERE allow`、`adb shell am set-standby-bucket 包名 active`，重启后仍生效；root 额外可把 App 装成系统应用拿签名级权限、直接改系统数据库加白名单（不用 ADB）。
  - ❌ 解决不了语音唤醒的耗电：麦克风持续开着就是持续耗电，跟权限无关。
  - ⚠️ ADB 方案的门槛：要连电脑、开 USB 调试——分享给别人时对方得会这一步。
- **建议**：做成**可开关的可选功能，默认关闭**。开启时接受常驻通知和耗电；关闭时回到休眠模式。请讨论这是否可接受，或是否有更省电的折中（如只在亮屏时监听）。

**语音转文字的技术选型**（离线优先，符合无后端约束）：

- 唤醒词检测：Sherpa-ONNX / Porcupine / Vosk
- STT：Sherpa-ONNX / Vosk / whisper.cpp（离线）；不引入云服务，保持「语音数据不出本机」
- 链路：唤醒词 → 录音 → STT 转文字 → 作为用户输入发给官方大模型 API → TTS 念回复

**快捷入口已改定（本次）**：放弃长按电源键 0.5s（第三方 App 做不到，且 root 后要刷模块、破坏可分享性），改为**通知栏常驻快捷入口**——常驻一条通知，点一下直接进 App 对话。普通 App 即可实现，不需要 root，且进程仍可休眠（点通知才拉起），不违背省电设计。设置里加开关控制这条常驻通知的显示/隐藏。

**读取手机自带天气 App 的数据（本次评估并放弃）**
- **放弃原因**：Android 没有公开的标准天气数据接口，各厂商天气 App 数据不对外开放、不提供个人开发者 SDK。root 后可硬读私有数据文件（如 sqlite），但格式私有、系统升级就变、每家不同，且分享给别人时对方未必 root。厂商天气 App 本身也是调第三方气象 API，直接调 Open-Meteo 更稳。

## 五、给讨论方的重点问题

请重点讨论以下几点：

1. **~~A 方案三层记忆 + 快捷反馈的负分机制~~（已定）**：打分规则三种状态——默认不加不扣（只按淡忘分衰减）；回复了主动消息 → 对应记忆加分；点 1 次「别提这个」→ 降权 + 30 天冷却、到期恢复；点 2 次 → 永久拉黑（不删记忆，主动问仍答）。所有记忆被否时退回环境钩子，仍无则跳过。不再讨论。

2. **~~心情 mood 字段的更新逻辑~~（已定）**：用一次额外的独立模型调用更新（不占主对话上下文、用轻量模型、失败保持原值），不用本地规则。不复用会话 ID。不再讨论。

3. **~~特殊日期与事件预约的冲突~~（已定）**：生日/纪念日存长期记忆（录一次），每天定时检查时命中日期则强制设为当天钩子优先发；一次性事件（明天面试）仍走 setAlarmClock 精确闹钟。不用维护事件表/repeat 字段/续期逻辑。不再讨论。

4. **~~C 方案双调度撞车~~（已定，A+C）**：所有触发源统一投进一个「待发队列」，由一个调度器串行处理（解决并发竞态 + 规则集中一处）；出队时按优先级选——用户指令提醒 > 追问链 > 事件预约 > 环境钩子 > 定时兜底闲聊（解决重要提醒被挤掉）；冷却/勿扰/每日上限作为最后闸门在出队时统一检查。不用原子锁方案（会挤掉重要提醒）。不再讨论。

5. **~~记忆干预界面的数据一致性~~（已定，方案 A 不管）**：用户改记忆时若正好有生成任务用了旧记忆 → 那条消息照常发（基于旧记忆），不取消不重来。冲突窗口极小、后果轻；每次生成都重新读记忆库，所以下一次一定用新记忆。不引入版本号校验/任务取消机制。不再讨论。

6. **有没有遗漏的功能或更好的替代方案**：尤其是「像真人」这个体验目标上。

7. **~~TTS 后台播放的实现~~（已定）**：默认后台自动念（设置里可关）；App 被唤醒后短暂停留 5 分钟，语音朗读期间保持进程与 WakeLock 存活、播完即释放。不再讨论。
8. **系统 TTS 引擎的选用（本次新增）**：开发者手机已装语音引擎；分享给别人时，若设备没有可用引擎，按既定策略明确提示「请安装语音引擎」，不内置离线引擎。请讨论：如何可靠检测引擎是否可用（含中文语音数据）？第三方引擎（如讯飞）如何在 `TextToSpeech` 里被正确枚举和选用？

9. **~~主动消息语音的触发时机~~（已定）**：通知弹出后后台自动念，设置里可关。（与问题 7 同一结论，不再讨论。）

10. **~~对话自动朗读的体验细节~~（已定）**：整段回复生成完后一次性念，不逐字念、不边生成边念。不再讨论。

11. **~~环境关心和记忆钩子的优先级~~（已定）**：环境钩子优先于记忆钩子（环境有时效性，错过就没意义）。不再讨论。

12. **~~定位的隐私与省电边界~~（已定）**：后台只读缓存位置、不主动定位；每天第一次打开 App 时前台更新一次缓存；只申请粗略位置、不存轨迹；一旦用户手动指定城市则不再自动定位。不再讨论。

13. **语音唤醒 vs 省电的取舍（本次新增，重点）**：语音唤醒需要常驻前台服务+麦克风，与「进程休眠」冲突；root/ADB 只能解决后台保活，解决不了麦克风耗电（小爱同学靠厂商 DSP，普通 App 拿不到）。请讨论：可开关默认关闭的方案是否可接受？有没有更省电的折中

14. **~~图片输入的具体参数~~（已定）**：用官方 API 图片能力；App 层面**不限制**格式/大小、**原图发送**不限缩、单轮**最多 10 张**。注意：官方 API 对图片格式/单张大小/分辨率各有硬限制，超限由 API 报错，App 需给出明确提示；原图 ×10 的 token 费用很高（按像素计费），用户自选、不强制压缩。不再讨论。

15. **~~底部状态栏数据的来源~~（已定）**：tok/s、缓存命中、上下文占用三项始终显示；API 没给数据的项显示占位符 `?? tok/s · 缓存命中 ??% · 上下文 ??%`，不隐藏、不伪造。不再讨论。

16. **~~用户能否关闭「手动打负分」功能~~（已澄清，无需开关）**：开发者本意不是要开关，而是明确打分规则——默认不加不扣、回复加分、点「别提这个」才扣分，无「不回复就扣分」。已写入模块 3，不再讨论。

## 六、验收标准（供执行者参考）

- 断网时 App 不崩溃，恢复联网后能继续工作
- 手动触发测试模式，能完整跑通：决策 → 三层记忆召回钩子 → 生成 → 顶部通知 → 点击进对话
- 自动勿扰模式：默认关闭；开启并处于勿扰区间时，主动消息不自动念语音，是否发通知按该模式独立开关执行（旧的硬编码静默时段已删除，统一由此机制管理）（本次新增）
- 一天主动消息不超过设置的上限（默认 3 条）
- 统一待发队列：多条触发同时发生时只发一条；按优先级选（指令提醒>追问链>特殊日期>环境>闲聊），不出现连发两条（本次新增）
- 同一个记忆钩子不会短时间内连续两次被召回（已提起标记生效）
- 记忆打分三态：默认不回复不点按 → 分数不变（只按淡忘分衰减）；回复了主动消息 → 对应记忆加分、更易召回；点「别提这个」1 次 → 30 天不主动提、到期恢复，点 2 次 → 永久拉黑但记忆不删（主动问仍能答）。所有记忆被否时退回环境钩子，仍无则跳过不发（本次新增）
- App 进程在两次唤醒之间完全退出，不常驻
- App 被唤醒后可短暂停留进程 5 分钟，以便用户进入 App 续上话题聊天；5 分钟到即结束，不无限驻留
- 记忆管理界面能看到三层记忆的内容、时间、权重，能手动增删
- 改记忆时若有生成任务正用旧记忆：该消息照常发（方案 A 不取消），下一次生成用新记忆（本次新增）
- 语音总开关关闭时，对话朗读和主动消息语音都不触发；开启时，点按消息能朗读、主动消息通知弹出后后台自动念、整段回复生成完后一次性念
- 自动勿扰模式：开关默认关闭；开启并处于勿扰区间时，主动消息不自动念语音；区间内是否发通知按该模式的独立开关执行；对话手动点按朗读不受勿扰影响（本次新增）
- 设备无可用 TTS 引擎时，App 不崩溃，明确提示「请安装语音引擎」（本次新增）
- 朗读期间 WakeLock 正常持有、播完释放，不因系统休眠中断语音（本次新增）
- 测试模式的完整链路包含语音环节（决策→召回→生成→通知→语音）（本次新增）
- 心情 mood：每轮对话后用一次独立模型调用更新，输出 JSON（mood + reason），不复用主对话会话 ID、不污染主对话上下文；失败时保持原 mood（本次新增）
- 特殊日期：生日/纪念日存长期记忆只录一次，每天定时检查命中日期时强制设为当天钩子发祝福，不需每年重设（本次新增）
- 内置节日表：公历节日日期写死、农历节日用预生成映射表（2026–2036 静态 JSON，运行时只查表不引入农历库）；用户无需录入，节日当天命中后基于人设+最近对话生成有语境的祝福，不发模板话（本次新增）
- 指令型提醒（「明天7点叫我起床」）：到点必发、带语音，绕过冷却/降频/无钩子闸门（勿扰模式除外）（本次新增）
- 追问型任务：说「7点提醒我吃早餐」→ 额外AI判断要不要追问/间隔/停止条件并存任务；7点问「吃早餐没」，回「吃了」→ 回「慢慢吃」结束，回「还没」→ 隔设定间隔再问、循环；「来不及不吃了」等语义变体能识别为停止；回复判定与 mood 合并为一次独立调用；到绝对上限或判断失败则停止（本次新增）
- 一次性事件（如明天面试）走 setAlarmClock 精确闹钟，与特殊日期机制并存（本次新增）
- 环境钩子优先于记忆钩子：两者都有时先用环境钩子，无合适环境钩子时才用记忆钩子（本次新增）
- 时间/天气/位置数据能正确进入生成层：夜间触发「别熬夜」类关心，高降水概率触发「带伞」类关心（本次新增）
- 无定位权限或定位失败时，可用手动指定城市继续工作，不崩溃（本次新增）
- 天气请求失败时 App 不崩溃，退化为只用时间做关心（本次新增）
- 同一类环境提醒在设定时间内不重复发送（本次新增）
- 每天第一次打开 App 时更新一次位置缓存；后台唤醒只读缓存、不主动定位；手动指定城市后不再自动定位（本次新增）
- 「关于」页标注「天气数据来自 Open-Meteo」并附链接（CC BY 4.0 署名要求）（本次新增）
- 前台打开 App 会自动联网拉一次天气并缓存；后台唤醒只读缓存（本次新增）
- 缓存天气超过 24 小时不发送天气类关心消息（本次新增）
- 语音唤醒关闭时，App 无前台服务、无常驻通知，保持休眠（本次新增）
- 语音唤醒开启时，唤醒词能被识别并进入对话，语音转文字→大模型→语音回复链路跑通（本次新增）
- 通知栏常驻快捷入口：开关打开时显示、点击直达对话页；关闭时不显示；App 进程仍保持休眠（本次新增）
- root/ADB 白名单方案：文档记录具体命令（Doze 白名单、RUN_ANYWHERE、standby bucket）供自用和分享时参考（本次新增）
- UI 空/对话态切换：无对话时显示中心图标+「你好，我想成为你生活中的一部分」，有对话时隐藏并显示消息（本次新增）
- 顶部栏三个入口（设置 / 勿扰 / 新建对话）可点并进入对应功能；有对话时显示「记忆」入口（本次新增）
- 「+」图片输入：用官方 API、原图发送、App 不限制格式大小、单轮最多 10 张；API 超限时给明确报错提示（本次新增）
- 底部状态栏三项始终显示，API 未返回数据的项显示占位符 `?? tok/s · 缓存命中 ??% · 上下文 ??%`，不隐藏不伪造（本次新增）
- 「记忆」入口在空状态和对话态都显示；底部聊天框在两种状态都显示（本次新增）
