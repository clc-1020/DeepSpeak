# 陪聊 APP 开发计划

> **状态：历史** ｜ v1 任务清单，已被第二版开发计划取代。
> 本文档随代码演进，细节以代码与本目录其他现行文档为准。

## 项目信息

- **技术栈**：Kotlin 原生 Android
- **目标系统**：Android（已 root）
- **开发方式**：蓝图先行 + 分功能迭代
- **API 费用**：用户自填 Key，承担所有费用

## 关键技术决策

1. **记忆语义去重**：本地 embedding 模型（`all-MiniLM-L6-v2`），相似度 > 0.85 判定重复
2. **记忆召回**：规则算分（时间新鲜度 × 权重 - 淡忘分）选 TOP 3，交给大模型挑话题
3. **mood 更新**：每 5 轮对话更新一次，独立 API 调用
4. **主动消息上限**：一天最多 n 条 AI 自发消息（默认 3，可调），不计入用户指令提醒和追问链
5. **主模型**：`deepseek-flash`（原生视觉、1M 上下文），陪伴默认关思考（`thinking:disabled`）
6. **上下文缓存**：人设+长期记忆摘要作稳定前缀，变化内容置后，吃缓存命中价
7. **结构化输出**：mood/记忆提取用 `response_format=json_object`
8. **时间/地域**：每轮 user 前注入 `latest_reminder`；新建会话开 `title:{enabled:true}`
9. **TTS**：系统 TTS 兜底 + DeepSeek 官方 TTS（`/v1/tools/tts`）可选双通道

> 详细设计与类/方法清单见 `陪聊APP-DeepSeek新API接入设计.md`。

### 阶段 2：记忆系统

#### 任务 2.1：本地 embedding 模型集成
- **内容**：
  - 集成 ONNX Runtime Android
  - 下载 `all-MiniLM-L6-v2` 模型（~80MB）到 `assets/` 或首次启动下载
  - 实现文本 → embedding 向量（384 维）
  - 实现余弦相似度计算
- **依赖**：1.1
- **验收标准**：
  - 同一句子两次编码，相似度 > 0.99
  - 语义相近句子相似度 > 0.85
  - 无关句子相似度 < 0.5
- **复杂度**：★★★★☆

#### 任务 2.2：记忆提取与存储
- **内容**：
  - 每轮对话后，额外 API 调用（不复用会话 ID）：
    - 输入：`system: "从对话中提取需要记住的信息，分类为短期/长期/日志，输出 JSON"` + 最近 3 轮对话
    - 输出：`{"short": [...], "long": [...], "daily": [...]}`
  - 解析 JSON，存入对应表
  - 失败保持原记忆，不影响主对话
- **依赖**：1.2, 1.4, 2.1
- **验收标准**：
  - 对话「我明天要面试」→ 短期记忆表新增一条
  - 对话「我对花生过敏」→ 长期记忆表新增一条
  - JSON 解析失败不崩溃
- **复杂度**：★★★☆☆

#### 任务 2.3：语义去重
- **内容**：
  - 新记忆生成 embedding
  - 与旧记忆库（同类别）计算余弦相似度
  - 相似度 > 0.85：更新旧记忆的 `content`、`timestamp`、`weight += 0.1`
  - 否则：插入新记忆
- **依赖**：2.1, 2.2
- **验收标准**：
  - 连续说两次「我明天要面试」→ 只保留一条记忆
  - 「我明天要面试」和「明天去公司面试」→ 合并为一条
- **复杂度**：★★★☆☆

#### 任务 2.4：时间锚点转换
- **内容**：
  - 提取记忆中的相对时间（「明天」「下周三」「3 天后」）
  - 转换为绝对日期（如 `2026-11-21`）
  - 存储时替换原文本（「明天面试」→「2026-11-21 面试」）
- **依赖**：2.2
- **验收标准**：
  - 「明天 7 点叫我起床」→ 存储「2026-11-21 07:00 叫我起床」
  - 「下周三开会」→ 存储「2026-11-27 开会」
- **复杂度**：★★☆☆☆

#### 任务 2.5：淡忘机制
- **内容**：
  - 短期记忆每天凌晨 `fadeScore += 时间衰减因子`（如 +0.1）
  - 召回时 `得分 = 权重 × 时间新鲜度 - fadeScore`
  - 30 天后 `fadeScore` 很高，基本召不回，但不删除
- **依赖**：2.2
- **验收标准**：
  - 新记忆优先召回
  - 30 天前的记忆基本不出现（除非权重极高）
  - 记忆管理界面仍可查看旧记忆
- **复杂度**：★★☆☆☆

#### 任务 2.6：记忆召回（规则算分）
- **内容**：
  - 算分公式：`得分 = 时间新鲜度 × weight + (当前时间 - 上次提起) × 久未提及加分 - fadeScore`
  - 选 TOP 3
  - 交给大模型：`system: "从以下记忆中选一个当话题"` + TOP 3 记忆
  - 返回选中的记忆 ID
- **依赖**：2.2, 2.5
- **验收标准**：
  - 同样条件下，新记忆排前面
  - 久未提及的记忆加分后能召回
  - 选中记忆后更新 `lastMentioned`
- **复杂度**：★★★☆☆

#### 任务 2.7：记忆管理界面
- **内容**：
  - 顶部「记忆」入口 → 三个 Tab（短期/长期/日志）
  - 列表显示记忆内容、时间、权重、淡忘分
  - 点击可编辑/删除/新增
  - 新增时手动选择类别
- **依赖**：2.2, 2.3, 2.5
- **验收标准**：
  - 能查看所有记忆
  - 手动添加「记住我对花生过敏」→ 成功存入长期记忆
  - 删除后从数据库移除
- **复杂度**：★★☆☆☆

#### 任务 2.8：打分三态（回复/别提这个）
- **内容**：
  - 主动消息通知添加三个按钮：「回复」「忽略」「别提这个」
  - 「回复」：对应记忆 `weight += 0.2`
  - 「别提这个」：第 1 次 `weight -= 0.5`、打「冷却」标记（30 天后恢复）；第 2 次打「拉黑」标记（永久）
  - 召回时跳过冷却/拉黑记忆
  - 用户主动问仍能答
- **依赖**：2.6, 3.4（主动消息通知）
- **验收标准**：
  - 点「别提这个」1 次 → 30 天内不召回该记忆
  - 点 2 次 → 永久不召回（记忆仍在库里）
  - 手动改记忆时，正用该记忆的主动消息照常发，下次用新记忆
- **复杂度**：★★☆☆☆

### 阶段 3：主动消息框架

#### 任务 3.1：统一待发队列
- **内容**：
  - 数据库表 `pending_messages`：id, type（指令提醒/追问/节日/环境/闲聊）, priority, content, triggerTime, state
  - 所有触发源往队列投任务，不直接发消息
  - 优先级：指令提醒(5) > 追问(4) > 特殊日期(3) > 环境(2) > 闲聊(1)
- **依赖**：1.1
- **验收标准**：
  - 多条消息同时触发，只发最高优先级那条
  - 同级按时间先后
- **复杂度**：★★☆☆☆

#### 任务 3.2：WorkManager 定时检查
- **内容**：
  - `PeriodicWorkRequest`，每 2 小时执行一次
  - 约束：`setRequiredNetworkType(CONNECTED)`
  - Worker 逻辑：检查决策闸门 → 召回记忆钩子 → 投入队列
- **依赖**：3.1
- **验收标准**：
  - 息屏、Doze 下仍能唤醒
  - 无网时不执行，恢复网络后执行
- **复杂度**：★★☆☆☆

#### 任务 3.3：AlarmManager 精确闹钟
- **内容**：
  - 用户说「明天 7 点叫我起床」→ 提取时间 + 任务描述
  - `setAlarmClock()` 设精确闹钟
  - 到点 BroadcastReceiver 触发 → 拿 WakeLock → 投入队列（优先级 5）
- **依赖**：3.1
- **验收标准**：
  - 到点必发（绕过冷却/降频/无钩子）
  - 能穿透深度 Doze
- **复杂度**：★★★☆☆

#### 任务 3.4：决策闸门（纯规则）
- **内容**：
  - 出队时检查（不调模型）：
    1. 勿扰模式：区间内按设置处理
    2. 冷却时间：距上次交互 < 2 小时 → 丢弃
    3. 一天上限：AI 自发消息今日已达 n 条（默认 3）→ 丢弃（不计入指令提醒和追问链）
    4. 回复率驱动：近 7 天回复率 < 20% → 降频到一天一次
    5. 无钩子：记忆钩子和环境钩子都召不出 → 丢弃
  - 通过所有闸门 → 生成消息
- **依赖**：3.1
- **验收标准**：
  - 刚聊过 1 小时，主动消息被拦截
  - 一天发满 3 条后，后续被拦截
  - 指令提醒（叫起床）绕过冷却/上限，但受勿扰约束
- **复杂度**：★★★☆☆

#### 任务 3.5：生成与送达
- **内容**：
  - 通过闸门后：钩子内容 + 人设 + 最近 3 条对话 + mood → API 生成消息
  - `NotificationCompat.Builder`，`IMPORTANCE_HIGH`，顶部弹出
  - 点击通知 → 打开 App 并插入对话历史
  - 语音开关开启 → 后台 TTS 念出来
- **依赖**：3.4, 4.1（TTS）
- **验收标准**：
  - 通知弹出并能点击进入对话
  - 消息插入对话历史（不重复）
  - 勿扰区间内不自动念语音（但可能发通知，取决于设置）
- **复杂度**：★★★☆☆

#### 任务 3.6：测试模式按钮
- **内容**：
  - 设置页「立即触发一次主动消息」按钮
  - 手动跑完整链路：决策 → 召回 → 生成 → 通知 → 语音
  - 绕过所有闸门（冷却/上限/勿扰）
- **依赖**：3.5
- **验收标准**：
  - 点击后立即收到通知
  - 消息有真实内容（基于记忆或当前时间）
- **复杂度**：★☆☆☆☆

### 阶段 4：语音输出（TTS）

#### 任务 4.1：TTS 基础实现
- **内容**：
  - 系统 `TextToSpeech` API
  - 设置页：引擎选择（`getEngines()`）、语速滑块、语音总开关
  - 无引擎时提示「请安装语音引擎」
  - 异步初始化（`onInit`），处理「初始化未完成就收到消息」的队列
- **双通道（2026-11-20 增补，见设计文档 §5）**：
  - 抽象 `TtsEngine` 接口；`SystemTtsEngine`（系统 TTS，兜底，离线）
  - `DeepSeekTtsEngine`（官方 `POST /v1/tools/tts`，返回 wav/pcm 音频流，联网、按字符计费）
  - `TtsManager` 按配置选择；官方 TTS 失败/无网自动降级系统 TTS
  - 设置页（7.1）加「语音通道：系统 / DeepSeek 官方（联网计费）」+ 音色 `stella`(女)/`tide`(男)
- **依赖**：1.3（UI）
- **验收标准**：
  - 枚举/切换引擎并选择；系统引擎能念
  - 调整语速后念出来能听出区别
  - 无引擎时不崩溃；官方 TTS 失败能降级系统 TTS
- **复杂度**：★★★☆☆

#### 任务 4.2：对话朗读
- **内容**：
  - 对话消息长按 / 点喇叭图标 → 朗读
  - 整段生成完后一次性念（不逐字、不边生成边念）
  - 朗读期间持有 WakeLock
- **依赖**：4.1, 1.4
- **验收标准**：
  - 点击能正确朗读
  - 朗读完自动释放 WakeLock
- **复杂度**：★☆☆☆☆

#### 任务 4.3：主动消息语音
- **内容**：
  - 通知弹出后后台自动念（不需点开通知）
  - 设置里「主动消息自动语音」开关
  - 勿扰区间内不自动念语音

## 待办增强：开机自动重排提醒（BOOT_COMPLETED）

> 记录于 2026-11-20 真机联调后。用户要求先记入计划、之后有空再做。

- **背景**：Android 重启会清空 AlarmManager 里所有闹钟；MIUI 的"划掉后台"更是直接 `force-stop`（日志 `SwipeUpClean: force-stop`），会取消该应用全部闹钟。当前提醒只在设钟时注册一次 → 重启或被强停后**静默丢失**。
- **目标**：重启手机后自动重排**尚未到点**的提醒；可选顺带补发**已错过**的提醒。
- **内容**：
  1. 排钟时把提醒**落库**：复用现有 `reminders` 表（`ReminderEntity`：type / taskDesc / triggerTime / state / priority），新增 `requestCode` 与 `memoryId`（关联 3.7 的短期记忆，便于「已完成」删除）。需 `AppDatabase` 升版本 + 迁移（当前用 `fallbackToDestructiveMigration`，注意别清数据的话要写正式迁移）。
  2. 新增 `BootReceiver`：manifest 注册 `android.intent.action.BOOT_COMPLETED`（再加 `com.android.intent.action.BOOT_COMPLETED`/厂商变体视需要），声明 `RECEIVE_BOOT_COMPLETED` 权限；`exported=true` 且只处理开机广播。
  3. 开机后查 `reminders where state=pending and triggerTime > now()` → 逐条 `AlarmScheduler.schedule(requestCode, triggerTime, taskDesc)` 重排（同 requestCode 覆盖，天然幂等）。
  4. `triggerTime <= now()` 的 pending 提醒：直接投递（入队 INSTRUCTION）或标记 `state=missed` 后由 App 启动时补发——二选一，建议"启动补发"更稳（开机广播时机可能被限制）。
  5. `state = DONE / CANCELLED` 的不重排、不补发。
  6. 完成/取消提醒时同步更新 `ReminderEntity.state`（与 3.7 的「已完成」回执打通）。
- **验收**：
  - 设「10 分钟后提醒」→ 重启手机（不重开 App）→ 到点仍弹通知；
  - 已点「已完成」的提醒重启后**不复活**；
  - 重启后未到点提醒在 `dumpsys alarm` 里能看到（`companion://reminder/*`）。
- **依赖**：3.3（精确闹钟）/ 3.5（送达）/ 3.7（已完成回执）。
- **复杂度**：★★☆☆☆（约 0.5 天）
- **边界**：`force-stop` 后（含 MIUI 划掉后台）**收不到开机广播也无法被拉起**，只能等用户手动打开一次 App 再补发；这是系统限制，无法绕过。用户侧应对：MIUI 省电策略设「无限制」+ 最近任务**锁定** App，避免被 `SwipeUpClean` 强停。

## 已知遗留（非阻塞·真机观察后决策）

> 记录于 2026-11-20 阶段 3、4 复核后。逻辑层全部完成并通过单测（287 用例全过），以下是延后处理的边界情况与可选优化项。

### 1. DB 迁移策略（上线前必改）
- **现状**：`AppDatabase` 当前用 `fallbackToDestructiveMigration()`（开发期可接受）。
- **影响**：升级 App 会清空本地对话历史 + 记忆 + 提醒。
- **建议**：正式发版前改为显式 `Migration`（写 `ALTER TABLE` + 兼容旧版）。
- **复杂度**：★☆☆☆☆（约 0.5 天）

### 2. 通知小图标（UI 细节）
- **现状**：`res/drawable/ic_notification.xml`（24dp 单色聊天气泡）。
- **可能问题**：`drawable-nodpi` 不随密度缩放，高 DPI 设备可能稍模糊。
- **建议**：真机观察，若模糊则换 `ImageVector`/`Icons` 或放 `drawable-xxxhdpi` 位图。
- **复杂度**：★☆☆☆☆（<0.5 天）

### 3. 主动消息频率控制（观察后决定）
- **待观察**：
  - 生成失败重试上限（当前无限重试，PENDING 积压会否过多）
  - 通知去重（当前无去重，5 分钟内多条同时到点是否打扰）
- **建议**：真机观察一周，按实际失败率 / 触发频率决定是否加「超 N 次自动 discard」或「5 分钟最多 1 条」。
- **复杂度**：★☆☆☆☆（<0.5 天）

### 4. 勿扰配置源统一（7.2 一起改）
- **现状**：
  - `ProactiveVoicePolicy` 已从 `ConfigRepository` 读 `dndEnabled`/`dndStartMinute`/`dndEndMinute`（4.3 完成）
  - `ProactiveGateConfig` 的 `dndEnabled` 仍写死 `false`（3.4 遗留）
- **影响**：闸门层勿扰未接设置页开关，但语音层已接（通知照发、语音静音）。
- **建议**：任务 7.2 实现勿扰模式时，统一改为从 `ConfigRepository` 读，让闸门也受勿扰控制。
- **复杂度**：★☆☆☆☆（0.2 天，7.2 顺带）

### 5. 半衰期 / 衰减因子配置化（观察后提升）
- **现状**：
  - `MemoryDecay.HALF_LIFE_DAYS = 7`（记忆新鲜度半衰期）
  - `MemoryFeedback.COOLING_DAYS = 30`（「别提这个」冷却天数）
  - 均为常量，MVP 阶段够用。
- **建议**：真机观察召回质量 / 用户反馈，若需微调再提升为 `AppState` 可配置项（设置页滑块）。
- **复杂度**：★☆☆☆☆（<0.5 天）

### 6. MainActivity 通知路由（UI 线）
- **现状**：`AndroidProactiveNotifier` 已写入 `intent.putExtra("conversation_id", conversationId)`。
- **待接**：`MainActivity.onCreate` 读 `intent.getLongExtra("conversationId", -1L)` + `chatViewModel.switchTo(id)`（UI 线负责）。
- **影响**：点通知打开 App 后不会自动跳到对应会话（需手动在侧边栏切）。
- **复杂度**：★☆☆☆☆（UI 线 <0.5 天）

### 7. 通知权限引导（设置页）
- **现状**：`AndroidProactiveNotifier` 当前无 `POST_NOTIFICATIONS` 权限时静默不崩（`catch SecurityException`）。
- **建议**：设置页（任务 7.1）加「通知权限」入口，检测未授予时引导去系统设置（`Settings.ACTION_APP_NOTIFICATION_SETTINGS`）。
- **复杂度**：★☆☆☆☆（7.1 顺带）

### 8. 精确闹钟权限引导（设置页）
- **现状**：`AlarmScheduler` 无精确权限时退回 `setAndAllowWhileIdle` + Toast 引导。
- **建议**：设置页加「精确闹钟权限」入口（用 `canScheduleExact()` 检测），引导去系统设置（`Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM`）。
- **复杂度**：★☆☆☆☆（7.1 顺带）

### 9. WakeLock 真机验收
